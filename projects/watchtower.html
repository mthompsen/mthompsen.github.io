Watchtower

A Windows desktop app and SQL Server database for a small SOC: triage Sigma alerts, run incidents through NIST SP 800-61 phases, and verify a tamper-evident audit log.

  • Audit chain: 9 TR_<TABLE>_Audit triggers write one AUDIT_ENTRY row per changed row. Each row hashes Audit_id, analyst, action, table, key, time, old and new JSON, and Prev_hash. IDs are gapless under an exclusive applock. Verification flags any ID gap, any Prev_hash mismatch, or any recomputed hash mismatch, and reports the first broken row. usp_VerifyAuditChain and AuditChainVerifier.cs run inside one SERIALIZABLE transaction.
  • Honest limits of the chain: the hash is unkeyed, so a sysadmin could rebuild every hash after an edit, truncate the tail, or disable a trigger without detection. Anchoring the chain head externally is listed as remediation, not built.
  • Least privilege: the app signs in with Windows auth, then sp_setapprole 'wt_app'. It is denied writes to AUDIT_ENTRY and EXECUTE on the append procedures. The analyst ID is fixed in a read-only SESSION_CONTEXT. Every write procedure re-checks role and active status through usp_Session_Require. The UI hides controls but is not the enforcement point.
  • Passwords use PBKDF2-HMAC-SHA256 with 600,000 iterations, a 16-byte salt and a constant-time compare. Accounts lock for 15 minutes after 5 failures, and unknown emails get the same response as wrong passwords. There is no dynamic SQL anywhere: free text is escaped by fn_ContainsPattern, and sort columns are checked against an allow list.
  • Integration tests cover every CHECK, FK and UNIQUE constraint, wrong-role denial on every write procedure, injection strings in every text filter, and app-role denial of SELECT * FROM ALERT and UPDATE AUDIT_ENTRY. They also check that both verifiers agree after 1,000 random operations and catch modified and deleted rows. Not built: MFA, idle timeout, an account management screen, or live detection (rules are stored, never executed).
